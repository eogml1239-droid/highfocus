# 크레딧 절약 모드

## 먼저 알아야 할 과금 사실

Kiro는 요청 "횟수"가 아니라 **크레딧을 0.01 단위로 분수 청구**한다. 출처: [Kiro Billing](https://kiro.dev/docs/billing/), [Billing FAQ](https://kiro.dev/docs/billing/related-questions/), [신규 요금제 발표](https://kiro.dev/blog/new-pricing-plans-and-auto/). (라이선스 준수를 위해 내용을 요약·재구성했다.)

| 사실 | 절약에 주는 의미 |
|---|---|
| 짧고 단순한 프롬프트는 1크레딧 미만 | 작은 작업을 쪼개는 건 손해가 아니다 |
| 복잡하고 긴 작업은 1크레딧 초과 | 한 턴에 무한정 몰아넣는 게 절약이 아니다 |
| vibe/spec 통합 풀, 스펙 태스크 실행은 보통 1크레딧 초과 | **잔량이 적을 때 스펙 워크플로는 금지** |
| 모델에 따라 소비량이 다르다 | 단순 작업은 저렴한 모델로 내린다 |

따라서 절약의 우선순위는 이 순서다.

```
1위  아예 Kiro를 호출하지 않는다      (0 크레딧)
2위  재작업·되묻기·탐색을 없앤다       (순수 낭비 제거)
3위  모델과 출력 길이를 낮춘다         (단가 인하)
```

가장 큰 낭비는 긴 작업이 아니라 **헛턴**이다. 되물어서 한 턴, 잘못 이해해서 다시 한 턴, 파일 찾느라 한 턴. 이 세 개를 없애는 게 절약의 본체다.

## 0단계 — 라우팅 (모든 요청에서 가장 먼저)

사용자 요청을 받으면 작업을 시작하기 전에 세 경로 중 하나로 분류한다.

### 무료 경로 (0 크레딧) — 최우선으로 밀어낸다

**기존 스킬 파일이 곧 완성된 프롬프트인 작업.** Kiro가 실행할 필요가 없다. 파일 경로만 알려주고 끝낸다.

- 룩북/피팅컷 생성 → `.kiro/skills/모델별피팅포즈시리즈/`
- 카테고리별 인식 프롬프트 → `.kiro/skills/여성남성카테고리별제미나이인식프롬프트/`
- 디테일컷 재구성 → `.kiro/skills/실물이미지디테일컷재구성/`
- 실사화 보정 → `모델별피팅포즈시리즈/CameraRaw실사화레시피.md`
- SNS 홍보글 → `.kiro/skills/SNS셀러말투홍보글작성/` + `하루치SNS게시글일괄생산/`
- 예약 발행 → `.kiro/skills/postiz/` (CLI라 사용자가 직접 실행한다. 게시물마다 나를 부르면 턴이 그만큼 나간다)

처리 방법은 `무료경로-매뉴얼.md`에 있다.

**이 경로일 때의 응답 형식** — 설명하지 말고 경로와 한 줄 안내만 준다.

```
무료 경로. 크레딧 안 씀.
→ .kiro/skills/모델별피팅포즈시리즈/여성A-168cm-48kg/포즈시리즈.md 열어서 프롬프트 복사
→ Gemini 웹에 사진 + 프롬프트 붙여넣기
막히는 지점 생기면 그때 불러.
```

### 저가 경로 (0.2~0.5 크레딧 예상)

- 파일 1개의 좁은 수정
- 이미 있는 파일에 항목 추가
- 짧은 사실 확인

**규칙:** 조사 없이 바로 편집한다. 요약하지 않는다. 완료 보고는 한 줄.

### Kiro 전용 경로 (1 크레딧 이상)

Kiro 말고는 할 수 없는 것만 여기로 온다.

- HIGHFOCUS Worker 코드 수정, 배포, 롤백
- 여러 파일에 걸친 판단이 필요한 변경
- 새 스킬·규칙 자산 만들기 (한 번 쓰면 이후 무료 경로가 되므로 투자 가치가 있다)
- `graphify` — 폴더를 전수 읽어 그래프를 만든다. **이 중 가장 비싸다**

**규칙:** 시작 전에 예상 비용과 대안을 한 줄로 알리고, 사용자가 진행하라고 하면 그때 한다. 잔량이 적을 때 몰래 큰 작업을 시작하지 않는다.

**graphify 추가 제한:** 잔량 50 미만이면 금지. 50 이상이어도 `--update`로 변경분만 돌리고 전체 재빌드는 하지 않는다. 이미 `graphify-out/`이 있으면 그 안의 `GRAPH_REPORT.md`를 열어 읽는다 — 이건 0크레딧이다.

## 절약 모드에서 내가 금지하는 행동

1. **되묻지 않는다.** 정보가 빠졌으면 합리적인 값을 가정하고 진행한 뒤, 가정을 결과 끝에 한 줄로 적는다. 확인 질문 한 번이 곧 한 턴이다.
2. **스펙 워크플로를 쓰지 않는다.** 요구사항→설계→태스크 승인 사이클은 턴을 많이 먹고 태스크 실행은 1크레딧을 넘는다. 잔량 30 미만이면 스펙 모드 제안 자체를 하지 않는다.
3. **서브에이전트를 호출하지 않는다.** context-gatherer, general-task-execution 모두 금지. 직접 좁게 읽는다.
4. **graphify, 전체 검색, 재귀 탐색을 하지 않는다.** 경로를 모르면 추측 대신 사용자에게 파일을 `#`로 붙여달라고 한 줄로 요청한다.
5. **읽은 파일을 다시 읽지 않는다.** 같은 세션에서 본 내용은 기억한다.
6. **요약과 재진술을 하지 않는다.** "무엇을 할지" 예고하지 않고, 끝낸 뒤 방금 한 말을 되풀이하지 않는다.
7. **묻지 않은 개선을 하지 않는다.** 리팩터링, 테스트 추가, 주변 정리 모두 금지.
8. **완료 보고는 3줄 이내.** 변경한 파일과 결과만.

## 사용자가 지켜주면 가장 크게 절약되는 것

- **모델을 내린다.** `/model`로 가벼운 모델 선택. 지금 이 대화 같은 무거운 모델은 배포·아키텍처 판단에만 쓴다.
- **한 번에 다 적는다.** `한번에요청-템플릿.md`를 복사해서 쓴다. 되물을 여지를 없애는 것이 목적.
- **파일은 `#`로 직접 붙인다.** 내가 찾아다니지 않게 한다.
- **결과가 틀렸으면 새 요청이 아니라 정정만 한다.** "3번 문장만 다시" 같은 좁은 정정이 전체 재생성보다 훨씬 싸다.
- **긴 대화를 이어가지 않는다.** 한 작업이 끝나면 새 세션으로. 대화가 길어질수록 매 턴 컨텍스트가 무거워진다.

## 예산 배분 (2026-09-22 기준, 잔량 100)

월급날을 10월 5일로 가정했다. 실제 날짜가 다르면 이 표를 고쳐라.

| 구간 | 기간 | 배정 | 하루 상한 |
|---|---|---|---|
| 1주차 | 9/22 ~ 9/28 | 35 | 5 |
| 2주차 | 9/29 ~ 10/5 | 35 | 5 |
| 비상 예비 | 상시 | 30 | — |

비상 예비는 **배포 사고, 사이트 장애, 월급날 지연**에만 쓴다. 게시글 만들기나 프롬프트 다듬기에는 쓰지 않는다.

하루 상한을 넘기려는 요청이 오면 진행 전에 알린다.

```
오늘 상한을 넘을 것 같아. 이 작업은 무료 경로로 돌릴 수 있어.
→ (경로 제시)
그래도 Kiro로 할까?
```

### 무엇에 우선 쓸 것인가

잔량이 줄어들수록 이 순서를 따른다.

1. **매출에 직결되는 것** — 판매 페이지에 올라갈 룩북컷 관련 막힘, 사이트 장애
2. **자산화되는 것** — 한 번 만들면 이후 무료 경로가 되는 스킬·규칙
3. 나머지는 월급날 이후로 미룬다

## 잔량 관리

- Kiro 사용량 표시에서 잔량을 확인한다. 나는 잔량을 직접 조회할 수 없으니, 정확한 숫자는 사용자가 알려줘야 한다.
- 잔량을 알려주면 `SKILL.md`의 예산 표를 그 값 기준으로 다시 계산해준다. (이 갱신 자체는 저가 경로다.)

### 잔량별 태세

| 잔량 | 태세 |
|---|---|
| 100 ~ 50 | 위 규칙대로. Kiro 전용 경로 허용 |
| 50 ~ 20 | 자산화 작업 중단. 사이트 장애와 매출 직결만 |
| 20 미만 | 전면 무료 경로. Kiro 호출은 사이트가 죽었을 때만 |
